# v0.1.3 — 窗口原生内存泄漏修复 + UI 看门狗自恢复

**日期**：2026-07-04
**Release**：https://github.com/yosh3289/speedforce/releases/tag/v0.1.3

## 一句话概括

用户反馈"运行一段时间后点托盘完全没反应、详情窗口打不开"再次复现。深入排查（Delve 抓活进程 + pprof 符号化 dump）确认：v0.1.2 的 goroutine 泄漏修复本身是对的，但**真正的故障是 fyne 事件循环被卡死（0 CPU、阻塞在 GL 层），并非 goroutine 泄漏**。同时排查中发现一个**独立的原生内存泄漏**（每次开关详情窗口漏 ~2 MB）。本版修掉内存泄漏，并加入**看门狗**在事件循环卡死时自动 dump 现场并重启恢复。

## 排查过程（为什么这次花了大力气）

之前 v0.1.2 把"跑一天后窗口打不开"归因为 subscribe goroutine 泄漏。这次同样的症状在**已含 v0.1.2 修复的正式二进制**上再次出现，说明那个解释不完整。

用 Delve attach 到卡死的活进程 + 自建 pprof 诊断构建，拿到确凿证据：

1. **不是 goroutine 泄漏**：卡死时只有 ~37 线程、~200 MB、~1050 句柄——量级正常。v0.1.2 的单常驻 subscribe 修复完好。
2. **不是探测卡住**：`http.Client.Timeout`(5s) 覆盖整个请求，调度器 tick 不会被网络探测永久卡住。
3. **是 fyne 主循环卡死**：进程活着（托盘图标在）但主循环 **0% CPU 阻塞**。Fyne 2.7.3 的 `runGL` 循环由 60 FPS ticker 驱动、`select` 排空 `funcQueue`，只有当**某个排队的 UI 函数或 GL 绘制调用永久阻塞**时才会卡死——典型诱因是机器休眠/锁屏/显示器断电后 **OpenGL 上下文丢失**，下一次窗口操作卡在 GPU 驱动里。
4. **无法合成复现**：本机清醒状态下狂开关窗口 **35 小时 / 2 万+ 次循环**，主循环始终健康（heartbeat `lat=0s`）。说明触发条件是环境事件（休眠/锁屏/GPU 复位），而非使用量。

排查中的意外收获——**原生内存泄漏**：35 小时压测中进程涨到 **22 GB 工作集 / 49 GB 提交**，但 Go 堆只有 1.1 GB、GDI/USER 句柄正常 → 泄漏在 **cgo/OpenGL 层**（每次开关窗口销毁 GL 上下文没释放，漏 ~2.3 MB）。注意：用户真正卡死时内存只有 200 MB，所以**这个泄漏不是卡死的原因**，是另一个独立 bug。

## 主要修复

### 1. 详情窗口原生内存泄漏（复用窗口而非反复销毁重建）
**问题**：每次打开"显示详情"都 `NewWindow`、每次关闭都销毁。Windows 上 GLFW 销毁的 GL 上下文没被完全释放，每个开/关循环漏 ~2.3 MB 原生内存（不在 Go 堆，GC 看不到）。
**根因**：反复创建/销毁 GL 上下文。
**修复**：详情窗口改为**创建一次、关闭时隐藏（`SetCloseIntercept` → `Hide`）、重开时复用**。同一个隐藏窗口 + GL 上下文全程复用，彻底消除开关churn。
- 语言运行时切换时，在**同一个窗口内**重建内容（不新建窗口），保留 v0.1.1 的语言即时生效行为。
- `update()` 仅在窗口可见时刷新。
**验证**：压测 ~200 次开/隐藏循环，内存从 220 MB 稳定在 235 MB（此前会涨 ~460 MB），后续完全持平。

### 2. UI 看门狗：事件循环卡死时自动 dump + 重启恢复
**问题**：一旦 fyne 主循环卡死（推测为休眠后 GL 上下文丢失），托盘和所有窗口全部无响应，且无法自恢复，只能手动杀进程重开。
**修复**：加一个**独立 goroutine 看门狗**（不依赖 fyne 循环）：
- 每 20s 探测一次主循环存活（往 `fyne.Do` 塞个函数看 30s 内是否执行）。
- **连续两次**超时（避开休眠/唤醒瞬间的误判）判定卡死。
- 卡死时先 `runtime.Stack` 把**全部 goroutine 现场**写到 `%APPDATA%\SpeedForce\wedge-<时间>.log`（即使 `-s -w` stripped 也能符号化，供事后定位真正的卡死点），再**重启自身**恢复。
- **防重启风暴**：10 分钟内最多重启 3 次（用环境变量跨重启计数），超了就停手不再拉起，避免死循环。
- 可用 `SF_NO_WATCHDOG=1` 关闭。

> 看门狗既是**自恢复**手段，也是**诊断埋点**：下次真在你机器上卡死，会自动留下带符号的 goroutine dump，就能一举定位那个 GL 卡死点、做针对性根治。

## 已知/未根治

- **卡死的根因（GL 上下文丢失）尚未根治**，只做了自动恢复。Fyne 框架层未暴露上下文丢失重建接口；等看门狗在真实场景抓到 dump 后再考虑上游修复或升级 Fyne。
- 设置窗口仍是每次重建（打开频率极低，泄漏可忽略），未改。

## 构建 / 工具链

- 本地首次 CGO 构建需要 MinGW（本机在 `E:\mingw64`，gcc 15.2.0 ucrt）。
- 排查用到：Delve（attach 活进程）、pprof（符号化 goroutine/heap dump）、`runtime.Stack`。

## 验证

- **内存泄漏修复**：压测 ~200 次开/隐藏循环，工作集从 220 MB 稳定在 235 MB 后完全持平（旧版会涨 ~460 MB）。
- **看门狗**：注入卡死后，连续两次探测超时 → 写出带符号的 goroutine dump（`goroutine 1 [select ...] ... glfw.runGL loop.go:149`）→ 自动重启（PID 变化）。防风暴：连续卡死时重启 3 次后停手（观测到 4 个 dump、3 次重启）。
- **单实例交接**：重启时先释放命名互斥量再拉起子进程，全程实例数恒为 1（不会出现 0 或长期 2）。
