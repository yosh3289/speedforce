# v0.1.5 — 设置窗口用 X 关闭后再也打不开的修复

**日期**：2026-10-07
**Release**：https://github.com/yosh3289/speedforce/releases/tag/v0.1.5

## 一句话概括

用户反馈“设置页面在一段时间之后也打不开了，就像之前的显示详情那样”。查明这**不是**托盘卡死那类问题，而是一个确定性的 bug：**只要用窗口右上角的 X 关过一次设置窗口，之后“设置”就再也打不开，直到程序重启。** 本版把设置窗口改成和详情窗口一样的“只创建一次、关闭只隐藏”。

## 根因

- 设置窗口原来的逻辑：首次打开时 `NewWindow` 并保存到 `w.win`；之后再打开就直接 `w.win.Show()`。只有点“保存”或“取消”（走自己的 `close()`）才会 `Close()` 并把 `w.win` 置空。
- 用 X 关闭时没有拦截，fyne 走默认流程把窗口**销毁**了，但 `w.win` 仍指向这个已销毁的窗口。
- fyne v2.7.3 的 `window.Show()`：`view()` 为 nil 且 `created` 已为 true 时**直接 return，不报错、不重建**。于是每次点“设置”都是对一个死窗口调用 Show，表现为“点了没反应”。
- 之所以像“过一段时间才犯”，是因为只有在某次用 X（而不是保存/取消）关掉之后才会触发。

**复现**（真实程序，向窗口发 `WM_CLOSE`，等同点 X）：打开设置 → 出现；X 关闭；再打开 → **不出现**；此时左键打开详情照常正常（界面循环是活的）。

## 修复

`internal/ui/settings/window.go`：
- 窗口只创建一次并复用；`SetCloseIntercept` 让 X 只**隐藏**窗口，“保存/取消”也改成隐藏。
- 每次打开都按当前配置**重建表单内容**（`buildFormLocked`），所以表单总是反映当前配置，取消掉的修改不会残留。
- `SetOnClosed` 兜底：万一窗口被真正关闭（例如程序退出），就丢掉引用，下次打开重新创建。
- 顺带避免了反复创建/销毁 OpenGL 窗口（v0.1.3 已证实这会泄漏原生内存）。

## 验证

- 测试先行：`TestSettingsReopensAfterWindowClosed`（Fyne 测试驱动：打开 → 关闭 → 再打开，断言出现的是一个仍处于打开状态的窗口），修复前失败、修复后通过。
- 推送前本地跑了与 CI 相同的 `golangci-lint`（v1.64.8）+ `go test ./...`，全绿（吸取 v0.1.4 的教训）。
- 真实程序端到端：连续三轮“打开 → X → 再打开”，每次都弹出且复用同一个窗口（同一 HWND），X 后为隐藏；托盘探测正常。

## 另一个发现（未修，记录在案）

修复前的进程在 2026-10-07 01:16 左右（用户正在逐项试用新功能）出现了一次**真正的 Fyne 界面卡死**，被看门狗抓到：`wedge-20261007-011715.log`，`ui_responsive=false tray_responsive=true`，goroutine 1 停在 `glfw._Cfunc_glfwPollEvents`（GLFW 分发窗口消息的原生代码）里；托盘正常。看门狗按设计自动重启恢复。这是第一次真正抓到 Fyne 主线程卡死的现场，**根因仍未知**。下一步（若再次出现）：在看门狗里对 GLFW 线程也发 `SendMessageTimeout(WM_NULL)`，区分“模态循环中仍在泵消息”（如拖动窗口）与“卡死在原生调用里”。
