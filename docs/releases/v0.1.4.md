# v0.1.4 — 托盘菜单卡死的真正根因修复 + 左键直接打开详情 + Claude/OpenAI 状态按钮

**日期**：2026-10-07（修复完成于 2026-07-07，本地实际使用泡测约 3 个月后发布）
**Release**：https://github.com/yosh3289/speedforce/releases/tag/v0.1.4

## 一句话概括

“运行一段时间后托盘菜单点了没反应、详情窗口打不开”这个反复出现的老毛病，这次终于抓到**确凿的现场证据**并定位到真正根因：**getlantern/systray 的 Win32 消息泵跑在一个没有锁定 OS 线程的 goroutine 上，运行数小时后被 Go 调度器迁移到别的线程，导致它再也收不到托盘窗口的消息——图标还在，菜单彻底死掉，0% CPU。** 这与 v0.1.2/v0.1.3 的两次推测（goroutine 泄漏、fyne GL 循环卡死）**都不是一回事**，那两次的诊断是错的。本版用一行 `runtime.LockOSThread()` 从根上修掉，并把看门狗扩展到同时监控托盘泵，补上之前的盲区。修复经过约 3 个月的实际使用验证后，同版本一并加入两个用户请求的小功能：**左键单击托盘图标直接打开详情**，以及**详情窗口里 Claude / OpenAI / Gemini 官方状态页的一键跳转按钮**。

## 排查过程（这次拿到了硬证据）

前两次都没能真正抓到卡死现场：v0.1.3 的看门狗只探测 fyne 事件循环，而这次的故障**恰恰不在 fyne**，所以看门狗从没触发过（同一个 PID 跑了 7 小时、没有任何 `wedge-*.log`、内存 94 MB 正常）。这一点本身就说明：**fyne 循环是活的，卡死的是别处。**

于是这次对**还活着的卡死进程**做了完整取证：

1. **确认不是 stale exe**：正在跑的就是 v0.1.3 正式包（二进制里有 watchdog / SetCloseIntercept 字符串，autostart 指向它），排除“旧程序”这个老坑。
2. **全内存转储**：用 `MiniDumpWriteDump`（PowerShell P/Invoke）对活进程抓了 600 MB 全内存 dump——**不影响进程存活**。Delve 对 `-s -w` stripped 的正式包无法符号化（`could not find goroutine array`），所以手写了一个 minidump 解析器（解析 ModuleList/ThreadList/Memory64List 三个流，按 x64 CONTEXT 的 Rip@0xF8 / Rsp@0x98 取栈，把栈上每个 qword 按模块地址区间归类）。
3. **行为对照**：让用户在卡死的活进程上实测——**托盘菜单根本弹不出来**（不是详情窗口单独的问题）。这把嫌疑从“fyne / 详情窗口”彻底转向 **systray 消息泵**。
4. **三重硬证据**（来自 dump）：
   - `SystrayClass` 托盘窗口由 **线程 14104** 创建、拥有；
   - 但此刻 **14104 正在跑网络 I/O**（栈上是 `ws2_32 / mswsock / sangfortcpx64` 这个 Winsock LSP），**根本没有在 GetMessage**；
   - 另一个**不拥有任何窗口**的线程 **30788** 却阻塞在 `user32!GetMessage`（由 Go 代码发起）——**这就是被迁移走的消息泵**；
   - 而 fyne 的 GLFW 窗口线程 13160 一切正常，印证“看门狗没触发”。

### 根因

Win32 规则：`GetMessage` **只**会取到“**创建该窗口的那个线程**”的消息。getlantern/systray 的设计假设 `systray.Run`（内含 `GetMessage` 消息泵）跑在 **main goroutine** 上——它的 `init()` 只 `LockOSThread` 了 goroutine-1。但本项目把 goroutine-1 让给了 fyne 的 GL 循环，systray 是用 `go t.Run()` 起的**普通、未锁定**的 goroutine。于是：

- 启动时消息泵和托盘窗口在同一个线程（14104），一切正常；
- 跑几个小时后，Go 调度器在某次阻塞系统调用/GC/调度点把消息泵 goroutine **迁移到别的线程**（30788），14104 这个 M 被复用去跑别的 goroutine（网络探测）；
- 从此消息泵在错误的线程上 `GetMessage`，永远收不到托盘窗口的点击 → **菜单永久失灵、图标还在、0% CPU、不会自愈**。

触发是**环境/时间驱动**的（迁移是偶发调度行为），所以表现为“跑一天后才犯”，且无法靠“狂点窗口”复现——与之前观察完全吻合。

## 主要修复

### 1. 把 systray 消息泵 goroutine 钉死在它的 OS 线程上（真正的根因修复）
`internal/ui/tray/tray.go` 的 `Run()` 里，在 `systray.Run(...)` 之前加一行 `runtime.LockOSThread()`（且不解锁）。这样消息泵 goroutine 终生固定在同一个 OS 线程上，托盘窗口的创建和 `GetMessage` 永远在同一线程 → 线程亲和性得到保证 → 菜单不再失灵。改动一行，风险极低（这本来就是 systray 期望的运行方式）。

### 2. 看门狗扩展：把托盘泵也纳入监控（补上盲区）
之前的看门狗只探测 fyne（`fyne.Do`），对 systray 泵的卡死**结构性失明**。本版新增 `platform.TrayPumpResponsive`：`EnumWindows` 找到本进程的 `SystrayClass` 窗口，用 `SendMessageTimeoutW(WM_NULL, SMTO_ABORTIFHUNG)` 探测消息泵是否还在处理消息。看门狗现在**同时**探测 fyne 循环和托盘泵，任一连续两次无响应即 dump + 重启。dump 文件里会写明是哪个子系统卡死（`ui_responsive=.. tray_responsive=..`）。

> 即使万一 `LockOSThread` 没能 100% 兜住所有情况，看门狗现在也能自动抓现场 + 重启，不会再出现“图标在、菜单死、只能手动杀进程”的局面。

## 新功能

### 1. 左键单击托盘图标 → 直接打开详情窗口
右键仍然弹出原菜单（显示详情 / 设置 / 退出），菜单里的“显示详情”保留。

- **换托盘库**：getlantern/systray v1.2.2 把左右键写死成同一个动作（`case WM_RBUTTONUP, WM_LBUTTONUP: showMenu()`），也没有任何点击回调，不换库做不到。改用它的维护分支 **fyne.io/systray v1.12.0**（Fyne 团队维护，接口几乎相同，多了 `SetOnTapped`）。核对源码确认：它**本来就已编译进程序**（Fyne 自身依赖它）；托盘窗口类名同样是 `SystrayClass`、同样在调用 `Run` 的 goroutine 上创建窗口并运行消息泵 → 上面的 `LockOSThread` 修复和看门狗托盘探测**原样有效**；Fyne 只在调用它自带的托盘 API 时才碰这个库，本项目不调用，不冲突。顺带去掉了 getlantern/systray 及其 8 个间接依赖。
- **关键设计（与上面的卡死同源）**：左键回调是在**托盘消息泵线程里、窗口过程内同步执行**的。回调里只要有一点阻塞，就会重现“菜单点不动”。所以 `onTapped` 只往一个容量为 1 的通道里**非阻塞地**丢一个信号（重复点击自动合并）就立即返回；真正打开窗口交给托盘事件 goroutine（`handleEvents`），和点“显示详情”菜单项走**完全相同的路径**。
- **没选的方案**：Fyne 2.7 自带托盘的 `SetSystemTrayWindow` 原生支持“左键开窗口”，但 `desktop.App` **没有 tooltip 接口**（悬停摘要是核心功能），且等于重写刚修好的托盘模块，不划算。

### 2. 详情窗口：Claude / OpenAI / Gemini 官方状态页一键跳转
底部一行三个等宽按钮“Claude 状态 / OpenAI 状态 / Gemini 状态”，分别打开 `status.claude.com`、`status.openai.com`、`aistudio.google.com/status`；“设置”挪到下一行。原来的“查看 Gemini 官方状态”按钮并入这一行、改成短文案。按钮由一张 `statusPages` 表生成，加新服务商只需加一行 + 文案。

### 3. 默认 Anthropic 状态源改用新域名
默认配置里的 Statuspage 源从 `status.anthropic.com` 改为 `status.claude.com`（旧域名现在 301 跳转到新域名）。只影响新装生成的默认配置；已有配置里的旧地址靠跳转照常工作。

## 经验

- **先拿硬证据再下结论**：前两次都是“看起来像”的推测，直到对活的卡死进程抓全内存 dump、逐线程看栈，才找到真正的机制。
- **在消息泵线程上跑的回调，任何阻塞都等于“菜单卡死”**：所以左键回调只投递信号，绝不在里面做事。
- **推送前要跑和 CI 一样的检查**：修复代码在本地泡测期间一直没提交，从没经过 CI；发布时本地只跑了 `go vet`/`go test`，CI 的 golangci-lint（`errcheck`）在 `traypump_windows.go` 抓到两处未接收的 Win32 调用返回值，导致打 tag 那次的 CI 在 Lint 步骤就失败（Test/Build 被跳过）。发布构建走的是不做 lint 的 Release 工作流，所以**已发布的程序不受影响**；随后用 `5452486` 修正（只是把返回值显式丢弃，行为不变）。以后发布前本地先跑 `go run github.com/golangci/golangci-lint/cmd/golangci-lint@latest run ./...`（与 CI 同版本，v1.64.8）。
